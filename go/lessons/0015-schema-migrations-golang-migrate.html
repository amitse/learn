Schema Migrations
with golang-migrate new

Keep your Postgres schema in sync with your code — across every environment.

Why Migrations Matter

In Lesson 0014 you connected your HTTP server to Postgres. But who created the table? Right now the answer is probably "I ran a SQL command manually." That breaks down the moment you have a second developer, a staging server, or a CI pipeline.

A schema migration is a versioned SQL script that transforms the database from one known state to another. A migration tool applies them in order, tracks which ones have already run, and lets you roll back if something goes wrong.

Key idea: Your migrations live in Git alongside your code. The schema is code.

TS → Go: The Mental Model

TypeScript (e.g. Prisma / Drizzle)
// schema.prisma or drizzle schema.ts
// Framework generates + runs SQL

// Run:
npx prisma migrate dev
npx drizzle-kit push
Go (golang-migrate, raw SQL)
// You write SQL yourself
// Tool tracks versions

// Run:
migrate -path ./migrations \
  -database $DATABASE_URL up

Go's ecosystem favours plain SQL migrations over schema-as-code abstractions. You get full SQL power and no magic — every change is readable in a diff.

File Layout

Each migration is a pair of files: up (apply) and down (rollback). They live in a migrations/ directory at the repo root.

myapp/
  cmd/api/
    main.go
  internal/
    …
  migrations/
    000001_create_tasks.up.sql
    000001_create_tasks.down.sql
    000002_add_due_date.up.sql
    000002_add_due_date.down.sql
  go.mod
  go.sum

Writing the SQL Files

000001_create_tasks.up.sql

CREATE TABLE tasks (
    id         UUID         PRIMARY KEY DEFAULT gen_random_uuid(),
    title      TEXT         NOT NULL,
    done       BOOLEAN      NOT NULL DEFAULT false,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

000001_create_tasks.down.sql

DROP TABLE IF EXISTS tasks;

000002_add_due_date.up.sql

ALTER TABLE tasks ADD COLUMN due_date TIMESTAMPTZ;

000002_add_due_date.down.sql

ALTER TABLE tasks DROP COLUMN due_date;
Never edit a migration that has already been applied to any shared environment. Add a new migration instead — just like you'd add a new Git commit rather than rewriting history.

Running Migrations (CLI)

Install the migrate CLI (one-time setup):

# macOS
brew install golang-migrate

# Linux / anywhere Go is installed
go install github.com/golang-migrate/migrate/v4/cmd/migrate@latest

Common commands

# Apply all pending migrations
migrate -path ./migrations -database "$DATABASE_URL" up

# Apply exactly 1 step
migrate -path ./migrations -database "$DATABASE_URL" up 1

# Roll back 1 step
migrate -path ./migrations -database "$DATABASE_URL" down 1

# See current version
migrate -path ./migrations -database "$DATABASE_URL" version

Running Migrations in Code (Optional Pattern)

Some teams run migrations automatically on server startup. This is convenient for development and simple deployments. Add the library as a dependency: 

go get github.com/golang-migrate/migrate/v4
go get github.com/golang-migrate/migrate/v4/database/postgres
go get github.com/golang-migrate/migrate/v4/source/file
import (
    "github.com/golang-migrate/migrate/v4"
    _ "github.com/golang-migrate/migrate/v4/database/postgres"
    _ "github.com/golang-migrate/migrate/v4/source/file"
)

func runMigrations(databaseURL string) error {
    m, err := migrate.New(
        "file://migrations",  // source: local files
        databaseURL,           // target: postgres connection string
    )
    if err != nil {
        return err
    }

    err = m.Up()
    if err != nil && err != migrate.ErrNoChange {
        return err  // ErrNoChange means "already up to date" — not an error
    }
    return nil
}

// In main(), call before starting the HTTP server:
if err := runMigrations(os.Getenv("DATABASE_URL")); err != nil {
    log.Fatalf("migrations failed: %v", err)
}
Note: The blank imports (_ "…/database/postgres" and _ "…/source/file") register the drivers as side effects — the same pattern as database/sql drivers.

How golang-migrate Tracks State

The first time you run migrate up, it creates a schema_migrations table in your database. It stores the current version number and a dirty flag. 

-- Created automatically by golang-migrate
SELECT * FROM schema_migrations;

--  version | dirty
-- ---------+-------
--        2 | false

If a migration fails halfway, the dirty flag is set to true and migrate up will refuse to run. Fix the database manually (or roll back with down 1), then run migrate force <version> to clear the flag.

Dirty state = migration crashed mid-flight. Don't panic: inspect what SQL ran, fix the DB, then migrate force N.
