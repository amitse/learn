Classify retryable upstream statuses

Your profile read may retry one eligible transport failure. An upstream can also answer HTTP successfully at the transport layer but return a status that represents a temporary gateway or service problem. Make that decision explicit—before the retry wrapper acts.

Tangible win: write and table-test a pure classifier that approves only 429, 502, 503, and 504 as candidates for the one already-approved retry.

A status is evidence, not permission

http.Client.Do normally returns a response for an HTTP 4xx or 5xx status; it is not automatically an error. The dependency adapter must inspect the response status and turn a selected one into an application error that the existing retry policy can recognize.

Narrow policy: retry only 429 Too Many Requests and the common intermediary/temporary service statuses 502, 503, and 504. Do not retry every 5xx; for example, 501 Not Implemented says this operation is unsupported, not briefly unavailable.

Put the decision in a pure function

func retryableUpstreamStatus(status int) bool {
    switch status {
    case http.StatusTooManyRequests, // 429
        http.StatusBadGateway,       // 502
        http.StatusServiceUnavailable, // 503
        http.StatusGatewayTimeout:   // 504
        return true
    default:
        return false
    }
}

This function does not sleep, issue a request, or choose an HTTP response for your own client. It answers one question only: “is this dependency response a candidate for the existing bounded retry?” The operation owner still limits the read to two total attempts.

Table-test the boundary

func TestRetryableUpstreamStatus(t *testing.T) {
    tests := []struct {
        name string
        code int
        want bool
    }{
        {"rate limited", http.StatusTooManyRequests, true},
        {"bad gateway", http.StatusBadGateway, true},
        {"service unavailable", http.StatusServiceUnavailable, true},
        {"gateway timeout", http.StatusGatewayTimeout, true},
        {"bad request", http.StatusBadRequest, false},
        {"not found", http.StatusNotFound, false},
        {"not implemented", http.StatusNotImplemented, false},
        {"internal server error", http.StatusInternalServerError, false},
    }
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            if got := retryableUpstreamStatus(tt.code); got != tt.want {
                t.Fatalf("retryableUpstreamStatus(%d) = %t, want %t", tt.code, got, tt.want)
            }
        })
    }
}

The negative cases carry the policy. A broad status >= 500 rule would silently change behavior for every future server status. Named cases make review and future policy changes deliberate.

TypeScript mental model

TypeScript / Node

function retryableStatus(s: number) {
  return [429, 502, 503, 504].includes(s)
}

const res = await fetch(url, { signal })
if (retryableStatus(res.status)) {
  throw new RetryableUpstreamStatus(res.status)
}

Go

resp, err := client.Do(req)
if err != nil { return Profile{}, err }
if retryableUpstreamStatus(resp.StatusCode) {
  return Profile{}, retryableStatusError{
    status: resp.StatusCode,
  }
}

Both inspect a received HTTP response rather than a network exception. In Go, remember to close a response body on every path where you received a response; that lifecycle detail belongs in the adapter, not in the pure classifier.

Keep outcomes distinct

  • Transport failure: no usable response arrived; Lesson 71’s error classifier assesses it.
  • Selected response status: a response arrived with one explicitly temporary code; this new classifier assesses it.
  • Other response status: do not retry merely because it is non-2xx. Map or decode it according to the dependency contract.
