Inject a deterministic request-ID generator

Lesson 59 made a random request ID at the HTTP boundary. That is right in production—but a handler test should not have to discover a random value and thread it through every assertion. Today you will make ID creation a tiny dependency, so a test can deliberately use req-test-42.

Tangible win: your test can prove the exact same request ID reaches the response header, request context, and structured error event.

The one idea

Inject the behavior that produces an ID, not a random package or a global variable. In Go, a named function type is a small interface: production supplies a secure generator; the test supplies a fixed function. This keeps the request-ID middleware deterministic without making production IDs predictable.

TypeScript / Node

type IDGenerator = () => string

const requestID = (makeID: IDGenerator) =>
  (req, res, next) => {
    const id = makeID()
    res.setHeader("X-Request-ID", id)
    next()
  }

Go / net/http

type IDGenerator func() (string, error)

func RequestID(next http.Handler,
    makeID IDGenerator) http.Handler {
  return http.HandlerFunc(func(w http.ResponseWriter,
      r *http.Request) {
    id, err := makeID()
    // attach id, then delegate
  })
}

Make one narrow seam

Name the dependency by what it does. A function signature communicates the only capability middleware needs. Returning an error lets the production implementation surface a rare randomness failure rather than silently falling back to a counter.
type IDGenerator func() (string, error)

func NewRandomID() (string, error) {
    b := make([]byte, 16)
    if _, err := rand.Read(b); err != nil {
        return "", fmt.Errorf("read random bytes: %w", err)
    }
    return hex.EncodeToString(b), nil
}

The crypto/rand package provides cryptographically secure random bytes. Keep that production choice outside the test.

Pass it into the middleware constructor. Generate once, before setting the header or deriving the context. The middleware still owns where the value goes; callers only choose how it is produced.
func RequestID(next http.Handler, makeID IDGenerator) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        id, err := makeID()
        if err != nil {
            writeJSONError(w, http.StatusInternalServerError,
                "internal server error")
            return
        }

        w.Header().Set("X-Request-ID", id)
        ctx := context.WithValue(r.Context(), requestIDKey{}, id)
        next.ServeHTTP(w, r.WithContext(ctx))
    })
}

handler := RequestID(mux, NewRandomID)

The standard library’s http.Handler contract is unchanged: middleware returns a handler that delegates to the next handler.

Use a fixed generator in the focused test. Now the test asserts the contract directly rather than merely checking that an unknown string is non-empty.
func TestRequestIDUsesGeneratedValue(t *testing.T) {
    const wantID = "req-test-42"
    makeID := func() (string, error) { return wantID, nil }

    next := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        if got := RequestIDFromContext(r.Context()); got != wantID {
            t.Errorf("context ID = %q, want %q", got, wantID)
        }
    })
    w := httptest.NewRecorder()
    RequestID(next, makeID).ServeHTTP(w, httptest.NewRequest("GET", "/", nil))

    if got := w.Header().Get("X-Request-ID"); got != wantID {
        t.Errorf("header = %q, want %q", got, wantID)
    }
}

Keep responsibilities separate

The generator produces an opaque string. The middleware puts that one string in the header and context. The handler reads it for an error event. Do not put a test-only constant in production wiring, and do not make the handler call the generator again—two generated values would break correlation.
