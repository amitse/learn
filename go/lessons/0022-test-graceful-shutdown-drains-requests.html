Test that graceful shutdown drains one request

Your server can bind an ephemeral listener. Now prove its shutdown contract: once a request has entered a handler, Shutdown waits for that request to finish instead of cutting its response off.

The contract worth testing

Server.Shutdown(ctx) first closes listeners, then waits for active connections to become idle. It returns when they are done or when ctx expires. That means a test must make the request definitely active before it starts shutdown—never use time.Sleep as a guess.

Node / TypeScript
const started = deferred<void>();
const release = deferred<void>();
app.get('/slow', async (_req, res) => {
  started.resolve();
  await release.promise;
  res.sendStatus(204);
});
// wait started → close → release
Go
started := make(chan struct{})
release := make(chan struct{})
mux.HandleFunc("GET /slow", func(w http.ResponseWriter, r *http.Request) {
    close(started)
    <-release
    w.WriteHeader(http.StatusNoContent)
})
// wait started → Shutdown → close(release)

Channels provide deterministic test coordination: closing started tells the test the handler is running; receiving from release deliberately holds it there. This is a small, focused use of the channel model from Lesson 11.

The test: observe waiting, then allow completion

func TestShutdownDrainsActiveRequest(t *testing.T) {
    started := make(chan struct{})
    release := make(chan struct{})
    mux := http.NewServeMux()
    mux.HandleFunc("GET /slow", func(w http.ResponseWriter, r *http.Request) {
        close(started)                 // signal: this request is active
        <-release                      // wait until test permits completion
        w.WriteHeader(http.StatusNoContent)
    })

    ln, err := net.Listen("tcp", "127.0.0.1:0")
    if err != nil { t.Fatal(err) }
    srv := &http.Server{Handler: mux}
    go func() { _ = srv.Serve(ln) }()
    t.Cleanup(func() { _ = srv.Close() })

    response := make(chan *http.Response, 1)
    requestErr := make(chan error, 1)
    go func() {
        resp, err := http.Get("http://" + ln.Addr().String() + "/slow")
        if err != nil { requestErr <- err; return }
        response <- resp
    }()

    <-started
    done := make(chan error, 1)
    go func() { done <- srv.Shutdown(context.Background()) }()

    select {
    case err := <-done:
        t.Fatalf("Shutdown returned early: %v", err)
    default:
        // Good: the active handler still prevents Shutdown from returning.
    }

    close(release)
    select {
    case err := <-requestErr:
        t.Fatal(err)
    case resp := <-response:
        defer resp.Body.Close()
        if resp.StatusCode != http.StatusNoContent {
            t.Errorf("status = %d, want %d", resp.StatusCode, http.StatusNoContent)
        }
    }
    if err := <-done; err != nil {
        t.Fatalf("Shutdown: %v", err)
    }
}
One subtlety: this is a teaching-sized test. In production test code, give the final select a generous timeout context so a regression fails rather than hanging forever. Do not use a timeout to establish ordering; use started and release for that.

Read the sequence

1Start the HTTP request in a goroutine; it cannot complete while the handler waits.

2Wait on <-started, then call Shutdown in another goroutine. A non-blocking select confirms it has not returned early.

3Close release. The handler writes 204, the client returns, and shutdown can now finish.

The Go http.Server.Shutdown documentation describes the listener-close and idle-wait behavior. The coordination primitives are standard channels; see the Go language specification.

Quick check

Choose an answer for instant feedback.

1. Why wait for <-started before calling Shutdown?

2. Immediately before close(release), what should the first non-blocking select observe?

3. What effect does close(release) have?

Ask your teacher: ask how to add a bounded timeout to the final wait without making this test flaky—or how to verify that a new request is rejected after shutdown begins.
