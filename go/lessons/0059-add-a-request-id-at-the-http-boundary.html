Add a request ID at the HTTP boundary

When an operator sees an unexpected-error event, a request ID lets them find the matching client report without putting the private error into the response. Today you will generate one ID per request, carry it in the request context, and use the same value in a response header and an error log.

Tangible win: every request to your operations route has one server-generated X-Request-ID that the client can quote and the server can log.

The one rule

Create the ID once at the HTTP boundary. Put it on the derived request context; downstream handlers read it but do not invent replacements. In Go, use a private key type for context.WithValue so unrelated packages cannot collide with a plain string key. The context package documentation explicitly recommends defining keys as an unexported type to avoid collisions.

TypeScript / Express

app.use((req, res, next) => {
  const id = crypto.randomUUID()
  req.requestId = id
  res.setHeader("X-Request-ID", id)
  next()
})

Go / net/http

func RequestID(next http.Handler) http.Handler {
  return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
    id := newRequestID()
    w.Header().Set("X-Request-ID", id)
    ctx := context.WithValue(r.Context(), requestIDKey{}, id)
    next.ServeHTTP(w, r.WithContext(ctx))
  })
}

Build the narrow seam

Define a private key and reader. Keep the typed key and the accessor in your transport package. A handler asks for the ID; it never knows the storage key.
type requestIDKey struct{}

func RequestIDFromContext(ctx context.Context) string {
    id, _ := ctx.Value(requestIDKey{}).(string)
    return id
}

The comma-ok assertion makes a missing value safe. Middleware is responsible for ensuring normal requests have one.

Generate an opaque, server-issued value. crypto/rand supplies cryptographically secure random bytes; hex.EncodeToString makes them header/log friendly. Do not accept a caller-provided correlation ID for this first version—otherwise a caller can choose confusing or forged log labels.
func newRequestID() string {
    b := make([]byte, 16)
    if _, err := rand.Read(b); err != nil {
        panic("generate request ID: " + err.Error())
    }
    return hex.EncodeToString(b)
}

This is process-initialization-grade randomness used per request. If your system has an availability policy for entropy failure, inject an ID generator and test that policy; do not silently use a predictable counter.

Wrap the mux once. Set the header before calling the next handler, then pass r.WithContext(ctx). That derived request is what carries the ID downstream.
mux := http.NewServeMux()
mux.HandleFunc("POST /ops/log-level", handleLogLevel)

handler := RequestID(mux)
server := &http.Server{Addr: cfg.Addr, Handler: handler}
Join the same value to the private error event. The response still says only internal server error; the ID is safe correlation metadata, not an explanation of the failure.
logger.Error("log-level change failed",
    "request_id", RequestIDFromContext(r.Context()),
    "error", err,
)
writeJSONError(w, http.StatusInternalServerError, "internal server error")

One focused test

Use a deterministic generator seam in production code if you want an exact assertion. The contract is simpler than the randomness: the response header and emitted log event must contain the same non-empty value.
