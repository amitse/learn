Error Handling Patterns in Go

No exceptions. No try/catch. Just values.

The Big Shift

In TypeScript, errors are thrown and caught — they travel invisibly up the call stack until something handles them. In Go, errors are ordinary return values. A function that can fail returns two things: the result, and an error. There's no try/catch, no implicit propagation. Every potential failure is visible right where it happens.

TypeScript 
// failure is invisible at call site
try {
  const user = await fetchUser(id);
  console.log(user.name);
} catch (err) {
  console.error(err);
}
Go 
// failure is explicit at call site
user, err := fetchUser(id)
if err != nil {
    log.Println(err)
    return
}
fmt.Println(user.Name)

The error type is a built-in interface with a single method: Error() string. Go spec ↗ 

// the error interface — built into Go
type error interface {
    Error() string
}

Creating Errors

Two ways to create a simple error:

import (
    "errors"
    "fmt"
)

// 1. Static message — use when the message never changes
var ErrNotFound = errors.New("not found")

// 2. Dynamic message — use when you need to include runtime context
err := fmt.Errorf("user %d not found", userID)
Convention Error values starting with Err (e.g. ErrNotFound) are called sentinel errors. They're package-level variables meant to be compared against — the Go equivalent of a known error code.

Wrapping Errors with %w

When a function calls another function that fails, it's good practice to wrap the original error with added context. The %w verb in fmt.Errorf does this — it embeds the original error inside a new one, preserving the chain. fmt.Errorf docs ↗

TypeScript (naive) 
catch (err) {
  throw new Error(
    `loadUser failed: ${err}`
  );
  // original cause is lost
}
Go — wrap with %w 
user, err := loadUser(id)
if err != nil {
    return fmt.Errorf(
        "loadUser %d: %w", id, err,
    )
    // original error preserved
}

Now the caller gets a message like "loadUser 42: not found" and can still inspect the root cause.

Inspecting Wrapped Errors: errors.Is and errors.As

Because errors can be wrapped multiple layers deep, you can't use == to check the type or value. Two standard library functions handle this: errors.Is ↗ / errors.As ↗

TypeScript 
// check type
if (err instanceof NotFoundError) { }

// check value identity
if (err === ERR_NOT_FOUND) { }
Go 
// check value (sentinel)
if errors.Is(err, ErrNotFound) { }

// check type (custom error)
var notFound *NotFoundError
if errors.As(err, &notFound) { }

errors.Is — walks the error chain looking for an exact match against a target value. Use it with sentinel errors.
errors.As — walks the chain looking for a specific type, and fills in the pointer if found. Use it with custom error types.

Custom Error Types

Any struct that implements Error() string is an error. This lets you attach structured data to errors — useful for HTTP handlers that need to map errors to status codes. 

// Define a custom error that carries an HTTP status code
type AppError struct {
    Code    int
    Message string
}

func (e *AppError) Error() string {
    return fmt.Sprintf("[%d] %s", e.Code, e.Message)
}

// Constructor helpers
func NotFound(msg string) *AppError {
    return &AppError{Code: 404, Message: msg}
}
func BadRequest(msg string) *AppError {
    return &AppError{Code: 400, Message: msg}
}

Putting It Together: Errors in HTTP Handlers

This is where it all pays off. In your HTTP server (from lesson 7), you can now let service functions return typed errors, and translate them into the right HTTP status codes in one place: 

func handleGetUser(w http.ResponseWriter, r *http.Request) {
    id := r.PathValue("id")

    user, err := getUser(id)
    if err != nil {
        var appErr *AppError
        if errors.As(err, &appErr) {
            // typed error — use its HTTP code
            writeError(w, appErr.Code, appErr.Message)
        } else {
            // unknown error — generic 500
            writeError(w, 500, "internal server error")
        }
        return
    }

    writeJSON(w, 200, user)
}

func getUser(id string) (*User, error) {
    if id == "99" {
        return nil, NotFound("user not found")
    }
    return &User{Name: "Amit"}, nil
}
The pattern: Service functions return typed errors with semantic meaning. Handlers translate errors to HTTP responses. This separates business logic from HTTP concerns — the same pattern as Express middleware in TS.
