Testing HTTP Handlers in Go

Lesson 9 net/http/httptest table-driven tests ~10 min

You have a working HTTP server with routing, JSON, middleware, and error handling. The final missing piece: how do you verify it actually works? Go ships a built-in package — net/http/httptest — that lets you fire real HTTP requests at your handlers without binding a network port. No Jest, no supertest, no framework needed.

1 — Test files & the testing package

Go tests live in files ending in _test.go, right next to the code they test. The testing package is part of the standard library — no install required. (pkg.go.dev/testing)

TypeScript (Jest) 
// handlers.test.ts
import { describe, it, expect } from 'vitest'

describe('GET /hello', () => {
  it('returns 200', async () => {
    const res = await fetch('http://localhost:3000/hello')
    expect(res.status).toBe(200)
  })
})
Go 
// handlers_test.go
package main

import (
  "net/http"
  "net/http/httptest"
  "testing"
)

func TestHelloHandler(t *testing.T) {
  req := httptest.NewRequest("GET", "/hello", nil)
  w   := httptest.NewRecorder()
  helloHandler(w, req)

  if w.Code != http.StatusOK {
    t.Errorf("expected 200, got %d", w.Code)
  }
}

Run all tests from your module root:

go test ./...
Key difference from TS In Jest you need a running server or a mock. In Go, httptest.NewRecorder() is a fake http.ResponseWriter — you call your handler function directly, passing the recorder instead of a real connection. No server, no network.

2 — The two httptest primitives

Type / FunctionWhat it isKey fields/methods
httptest.NewRequest(method, url, body) Creates a fake *http.Request (no network involved) .Header.Set(...), .Body
httptest.NewRecorder() Fake http.ResponseWriter that records what your handler writes .Code (status), .Body (buffer), .Header()
w.Result() Convert recorder to a real *http.Response Useful if you want json.Decode on the response body

pkg.go.dev/net/http/httptest#ResponseRecorder

3 — Table-driven tests: Go's idiom

Go codebases almost universally use table-driven tests — one slice of test cases, iterated in a loop. No describe/it nesting needed; the table is the documentation. (go.dev/wiki/TableDrivenTests) 

func TestGreetHandler(t *testing.T) {
  tests := []struct {
    name       string
    url        string
    wantStatus int
    wantBody   string
  }{
    {"valid name",    "/greet/amit", 200, "Hello, Amit"},
    {"empty name",    "/greet/",     400, "name required"},
    {"unknown route", "/nope",       404, ""},
  }

  for _, tt := range tests {
    t.Run(tt.name, func(t *testing.T) {
      req := httptest.NewRequest("GET", tt.url, nil)
      w   := httptest.NewRecorder()
      greetHandler(w, req)

      if w.Code != tt.wantStatus {
        t.Errorf("status: got %d, want %d", w.Code, tt.wantStatus)
      }
      if tt.wantBody != "" && !strings.Contains(w.Body.String(), tt.wantBody) {
        t.Errorf("body: %q not in %q", tt.wantBody, w.Body.String())
      }
    })
  }
}
t.Run(name, func) Each case runs as a named sub-test. On failure, Go prints TestGreetHandler/valid_name — instantly tells you which case failed. Equivalent to Jest's it('valid name', ...).

4 — Testing a JSON response

When your handler writes JSON, decode the recorder body with json.Decoder and assert field values directly — no string matching required. 

func TestCreateUser(t *testing.T) {
  body := strings.NewReader(`{"name":"Amit","email":"amit@example.com"}`)
  req  := httptest.NewRequest("POST", "/users", body)
  req.Header.Set("Content-Type", "application/json")
  w := httptest.NewRecorder()
  createUserHandler(w, req)

  if w.Code != http.StatusCreated {
    t.Fatalf("expected 201, got %d — body: %s", w.Code, w.Body.String())
  }

  var resp struct {
    ID   int    `json:"id"`
    Name string `json:"name"`
  }
  if err := json.NewDecoder(w.Body).Decode(&resp); err != nil {
    t.Fatal("invalid JSON in response:", err)
  }
  if resp.Name != "Amit" {
    t.Errorf("name: got %q, want %q", resp.Name, "Amit")
  }
}
t.Fatal vs t.Errorf Use t.Fatal / t.Fatalf when you want to stop the test immediately (e.g., bad JSON means the field assertions below are meaningless). Use t.Errorf when you want to keep running and collect all failures.

5 — Useful go test flags

CommandWhat it does
go test ./...Run all tests in all packages
go test -v ./...Verbose — print each t.Run name
go test -run TestGreetRun only tests matching the regex
go test -count=1 ./...Disable test result caching (always re-run)
go test -cover ./...Show per-package statement coverage %
No separate test runner to install Unlike TS where you pick Jest vs Vitest vs Mocha, Go's test runner is built into the toolchain. go test is the only command you'll ever need.
