Read module build info

Your lifecycle logs already carry linker-stamped version and revision. Now learn the small diagnostic tool Go can embed automatically: runtime/debug.ReadBuildInfo.

Tangible win: add a safe “best available” module version to one startup log, without making a handler depend on build metadata.

One concept: metadata has two sources

TypeScript mental model

A bundler or CI typically replaces a source value such as BUILD_VERSION. Your code reads the injected value at runtime.

Go

Go supports linker-stamped variables, and may also record module/build settings in the executable. ReadBuildInfo reads the latter if it is available.

SourceBest forImportant limit
linker -X main.version=…Your explicit release contractOnly values your build command supplies
debug.ReadBuildInfo()Diagnostic module and VCS settingsIt can return ok == false; settings can vary by build mode

Do not treat build info as request data. It still belongs at the application boundary—near startup logs—not in a response or handler.

Use it defensively

The function returns (*debug.BuildInfo, bool). The boolean is the contract: only inspect the value when it is true. Main.Version is often "(devel)" for local builds, so retain the linker default as your human-facing fallback.

package main

import (
    "log"
    "runtime/debug"
)

var version = "dev" // CI may replace this with -X main.version=v1.4.0

func moduleVersion() string {
    info, ok := debug.ReadBuildInfo()
    if !ok || info.Main.Version == "" || info.Main.Version == "(devel)" {
        return version
    }
    return info.Main.Version
}

func logStarting(logger *log.Logger) {
    logger.Printf("HTTP server starting version=%s", moduleVersion())
}

That is intentionally boring: one pure-ish selector, one boundary-owned log call. Your existing revision linker variable remains the precise source identity; this lesson only supplies a useful fallback/readout for module builds.

Do the 3-minute implementation

  1. Add runtime/debug and the moduleVersion function above beside your existing build variables.
  2. Call it from the startup lifecycle log, not from an HTTP handler.
  3. Run go run .. A local checkout will usually log your explicit dev fallback.
  4. Keep the CI linker command that stamps version and revision. Explicit release metadata is still your stable deploy contract.
Why not replace linker variables?

ReadBuildInfo reports what the toolchain recorded; linker variables express the identity policy you control. Prefer the linker value for a named release and use build info as optional diagnostics or a fallback—not as a reason to remove the explicit contract.
