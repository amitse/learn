Table-test operations auth outcomes

Lesson 52 connected verified JWT claims to an operations Principal. Now prove the HTTP boundary preserves the three outcomes: no verified identity → 401; verified but not permitted → 403; permitted → 204.

Tangible win

You will write one table-driven httptest for the debug-level route. It asserts observable status codes and confirms that only the allowed request calls the sensitive control.

Test the contract, not token cryptography

JWT signature validation belongs in middleware tests. This handler test starts after middleware has either put typed claims in the context or not. That makes the authorization mapping and HTTP response contract fast and unambiguous.

State the outcome matrix first

Context evidenceAuthorization resultHTTP resultControl called?
No typed claimsCannot construct a principal401No
Verified viewer claimsPrincipal lacks logs:write403Yes; it denies
Verified operator claimsPrincipal has logs:write204Yes; it changes level
Important boundary: do not make “viewer” into a fake missing identity just to obtain 401. A valid viewer token is evidence of identity; authorization must visibly deny it with 403.

Use a narrow control spy

The handler needs only an operation that receives a principal and returns an error. A small spy records calls without a mutable global logger or a real network listener.

type levelSetter interface {
    Set(context.Context, auth.Principal, slog.Level) error
}

type setSpy struct {
    calls int
    err   error
}

func (s *setSpy) Set(_ context.Context, _ auth.Principal, _ slog.Level) error {
    s.calls++
    return s.err
}

Your production LogLevelControl satisfies this interface. Keep the interface at the consumer boundary—the handler—so it describes exactly what the handler uses.

One table, three meaningful rows

func TestSetDebugAuthOutcomes(t *testing.T) {
    claimsContext := func(role string) func() context.Context {
        return func() context.Context {
            claims := &auth.Claims{RegisteredClaims: jwt.RegisteredClaims{
                Subject: "user-7",
            }, Role: role}
            return context.WithValue(context.Background(), auth.ClaimsKey, claims)
        }
    }

    tests := []struct {
        name       string
        context    func() context.Context
        controlErr error
        wantStatus int
        wantCalls  int
    }{
        {"missing claims is unauthorized", func() context.Context {
            return context.Background()
        }, nil, http.StatusUnauthorized, 0},
        {"viewer is forbidden", claimsContext("viewer"), ErrForbidden,
            http.StatusForbidden, 1},
        {"operator changes level", claimsContext("operator"), nil,
            http.StatusNoContent, 1},
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            control := &setSpy{err: tt.controlErr}
            h := SetDebug(control)
            r := httptest.NewRequest(http.MethodPost, "/ops/log-level/debug", nil)
            r = r.WithContext(tt.context())
            w := httptest.NewRecorder()

            h.ServeHTTP(w, r)

            if w.Code != tt.wantStatus { t.Fatalf("status = %d, want %d", w.Code, tt.wantStatus) }
            if control.calls != tt.wantCalls { t.Fatalf("calls = %d, want %d", control.calls, tt.wantCalls) }
        })
    }
}
Make the forbidden row truthful. In the real design, LogLevelControl.Set independently checks principal.Can("logs:write") and returns ErrForbidden. The spy shown here supplies that result to focus this test on the handler’s translation. Retain Lesson 51’s control test, which proves denial has no state or audit side effect.

Why check calls as well as status?

A 401 result alone does not prove the handler returned before the sensitive operation. Requiring zero calls for absent claims protects the authentication boundary. For 403, one call proves the handler passed a real principal to the control, which remains the operation-level authorization owner.
