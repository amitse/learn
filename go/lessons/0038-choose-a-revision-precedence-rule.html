Choose a revision precedence rule

Your binary can know its source revision in two places: the CI-owned linker variable from Lesson 36 and the optional vcs.revision setting exposed by build info. Pick one deterministic rule so startup logs never disagree ambiguously.

Tangible win: write a small, testable selector that uses an explicitly stamped revision when present and otherwise safely falls back to Go's recorded VCS revision.

One concept: an explicit value wins

TypeScript mental model

Prefer a CI-injected GIT_SHA; use optional bundler metadata only if the explicit environment value is missing.

Go

Prefer linker-stamped revision; use the vcs.revision build setting only when that explicit value is its local fallback.

CandidateRoleRule
revision linker variableIntentional release identityUse it unless it is the local fallback "none".
vcs.revision build settingToolchain diagnostic fallbackUse it only when build info is available and the setting is non-empty.
neitherTruthful local resultLog "none"; do not invent a SHA.

This is not about finding the “most detailed” value. CI's linker value is the deploy contract you control. Build settings are useful evidence, but may be absent depending on how the binary was built.

Encode the policy as a pure selector

debug.BuildInfo.Settings is a slice of key/value pairs. Keep the runtime call at the edge; make the choice itself a plain function so tests can supply a small settings slice.

package main

import "runtime/debug"

var revision = "none" // CI: -X main.revision=$(git rev-parse HEAD)

type buildSetting struct { Key, Value string }

func selectedRevision(stamped string, settings []buildSetting) string {
    if stamped != "" && stamped != "none" {
        return stamped
    }
    for _, s := range settings {
        if s.Key == "vcs.revision" && s.Value != "" {
            return s.Value
        }
    }
    return "none"
}

func revisionForLog() string {
    info, ok := debug.ReadBuildInfo()
    if !ok { return selectedRevision(revision, nil) }
    settings := make([]buildSetting, 0, len(info.Settings))
    for _, s := range info.Settings {
        settings = append(settings, buildSetting{s.Key, s.Value})
    }
    return selectedRevision(revision, settings)
}

The adapter is deliberately small. An equally good production design is to let selectedRevision accept []debug.BuildSetting directly; the lesson's tiny type makes its policy test independent of runtime discovery.

Prove the three outcomes

func TestSelectedRevision(t *testing.T) {
    tests := []struct {
        name, stamped string
        settings      []buildSetting
        want          string
    }{
        {"stamped beats build info", "a1b2", []buildSetting{{"vcs.revision", "c3d4"}}, "a1b2"},
        {"falls back to VCS setting", "none", []buildSetting{{"vcs.revision", "c3d4"}}, "c3d4"},
        {"honest local fallback", "none", nil, "none"},
    }
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            if got := selectedRevision(tt.stamped, tt.settings); got != tt.want {
                t.Fatalf("got %q, want %q", got, tt.want)
            }
        })
    }
}
