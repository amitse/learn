context.Context in HTTP Handlers

📅 Lesson 12 Go for TS Devs ~8 min

Every http.Request carries a context.Context. It tells your handler when the client has disconnected, when a deadline has passed, and lets you pass request-scoped values (like a request ID) down through the call stack — without touching function signatures all the way.

This is the last piece before you can write production-grade HTTP handlers. Let's make it concrete.

1. The TypeScript mental model

If you've used AbortController in the browser or in Node's fetch, you already know the idea:

TypeScript
const controller = new AbortController();
const { signal } = controller;

fetch("/api/data", { signal });

// cancel if client navigates away
signal.addEventListener("abort", () => {
  console.log("cancelled");
});

controller.abort(); // trigger cancellation
Go
// context is passed as first arg by convention
func fetchData(ctx context.Context) {
  req, _ := http.NewRequestWithContext(
    ctx, "GET", "/api/data", nil,
  )
  // if ctx is cancelled, the request stops
  http.DefaultClient.Do(req)
}

context.Context is Go's universal cancellation signal. It flows in through every function that does I/O — database queries, outbound HTTP calls, file reads — so any of them can stop work early if the client gives up.

2. What context.Context actually is

It's an interface with four methods. You'll rarely call them directly, but knowing them de-mystifies the whole API:

type Context interface {
  Deadline() (deadline time.Time, ok bool)  // when will this context expire?
  Done()     <-chan struct{}                 // closed when context is cancelled
  Err()      error                            // why it was cancelled
  Value(key any) any                         // look up a key/value pair
}
The only one you'll check directly: ctx.Done() — a channel that gets closed when the context is cancelled. You select on it to bail out of a slow operation.

3. r.Context() — your handler's built-in context

The HTTP server populates every request's context automatically. Pull it out with r.Context() and pass it to everything downstream:

func GetUserHandler(w http.ResponseWriter, r *http.Request) {
  ctx := r.Context()                        // ← get it here

  user, err := db.QueryUserContext(ctx, id)  // ← pass it everywhere
  if err != nil {
    // if the client disconnected, err will be context.Canceled
    http.Error(w, err.Error(), http.StatusInternalServerError)
    return
  }
  // ... encode response
}

If the client closes the connection mid-query, the database driver sees the context is cancelled and stops the query. You save CPU, memory, and DB connections — automatically.

4. Adding a timeout to an outbound call

A common pattern: you call a third-party API from your handler. You don't want to wait forever. Wrap the request context with a timeout:

func WeatherHandler(w http.ResponseWriter, r *http.Request) {
  // give the outbound call max 2 seconds
  ctx, cancel := context.WithTimeout(r.Context(), 2*time.Second)
  defer cancel() // ← ALWAYS defer cancel — prevents a goroutine leak

  req, err := http.NewRequestWithContext(ctx, "GET",
    "https://api.weather.io/current", nil)
  if err != nil { /* ... */ }

  resp, err := http.DefaultClient.Do(req)
  if err != nil {
    // could be context.DeadlineExceeded
    http.Error(w, "upstream timeout", http.StatusGatewayTimeout)
    return
  }
  defer resp.Body.Close()
  // ...
}
Always defer cancel(). context.WithTimeout and context.WithCancel start an internal goroutine. If you never call cancel(), that goroutine leaks until the parent context expires. The pattern ctx, cancel := ...; defer cancel() is idiomatic Go — you'll see it everywhere.

5. Checking if a client disconnected

For handlers with slow, multi-step processing, you can bail out early:

func SlowHandler(w http.ResponseWriter, r *http.Request) {
  ctx := r.Context()

  result1 := stepOne(ctx)

  // check between steps — no point continuing if client left
  select {
  case <-ctx.Done():
    // ctx.Err() is context.Canceled or context.DeadlineExceeded
    http.Error(w, "request cancelled", http.StatusRequestTimeout)
    return
  default:
    // context still alive, keep going
  }

  result2 := stepTwo(ctx, result1)
  // ...
}

The select with default is non-blocking — it checks the channel without waiting. Use this between expensive steps.

6. Storing values in a context

Middleware often attaches request-scoped data — like an authenticated user ID — so handlers don't need an extra parameter:

// internal/middleware/auth.go

type contextKey string  // private type — prevents key collisions
const userIDKey contextKey = "userID"

func AuthMiddleware(next http.Handler) http.Handler {
  return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
    userID := validateToken(r.Header.Get("Authorization"))

    // inject the user ID into the context
    ctx := context.WithValue(r.Context(), userIDKey, userID)
    next.ServeHTTP(w, r.WithContext(ctx))
  })
}

// internal/handlers/user.go
func GetProfileHandler(w http.ResponseWriter, r *http.Request) {
  userID, _ := r.Context().Value(userIDKey).(string)
  // use userID ...
}
Use a private type for context keys. If you use a plain string like "userID" as a key, any package can collide with it. A private named type (type contextKey string) in your package is package-scoped — no collision possible.
