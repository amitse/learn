Let Run react to cancellation

Lesson 25 gave Run ownership of Serve's terminal result. Now give it one input for “please stop,” so main supplies a signal and Run performs the HTTP shutdown.

One cancellation input; a fresh drain deadline

A cancellation context answers when to begin stopping. It is already done by the time Run receives it. Shutdown, however, needs a separate live context that gives active handlers time to drain. Do not pass the already-cancelled stop context into Shutdown.

Node / TypeScript
const stop = new AbortController()
process.on("SIGTERM", () => stop.abort())

await once(stop.signal, "abort")
await server.close() // its own grace period
Go
stop, cancel := signal.NotifyContext(
    context.Background(), syscall.SIGINT, syscall.SIGTERM,
)
defer cancel()

err := Run(stop, srv, ln, 5*time.Second)
Two contexts, two jobs: stop tells the lifecycle owner to begin shutdown. drainCtx bounds how long graceful shutdown may wait.

The lifecycle boundary

func Run(stop context.Context, srv *http.Server, ln net.Listener, grace time.Duration) error {
    served := make(chan error, 1)
    go func() { served <- srv.Serve(ln) }()

    select {
    case err := <-served:
        return normalServeResult(err)
    case <-stop.Done():
        drainCtx, cancel := context.WithTimeout(context.Background(), grace)
        defer cancel()

        if err := srv.Shutdown(drainCtx); err != nil {
            return err
        }
        return normalServeResult(<-served)
    }
}

func normalServeResult(err error) error {
    if errors.Is(err, http.ErrServerClosed) { return nil }
    return err
}

1Serve still runs concurrently because it blocks.

2The select waits for either an unexpected serve result or the stop signal.

3Once stop.Done() is closed, create a new timeout context for the drain.

4After a successful Shutdown, wait for Serve to finish and preserve Lesson 25’s ErrServerClosed → nil rule.

Keep signal plumbing at the edge

signal.NotifyContext belongs in main, where the process meets the OS. Run only depends on context.Context, so a test can cancel it directly—no real signal required. The standard library documents that NotifyContext cancels its context when a listed signal arrives; always call its returned stop function to restore normal signal behavior.

func main() {
    stop, cancel := signal.NotifyContext(context.Background(),
        syscall.SIGINT, syscall.SIGTERM)
    defer cancel()

    if err := Run(stop, srv, ln, cfg.ShutdownTimeout); err != nil {
        log.Fatal(err)
    }
}

Quick check

Choose an answer for instant feedback.

1. Why not call srv.Shutdown(stop) after receiving <-stop.Done()?

2. Why should Run accept a context.Context rather than listen for SIGTERM itself?

3. After Shutdown returns nil, what should Run do?

Ask your teacher: ask for the smallest deterministic test that cancels Run and proves a request drains before it returns.
