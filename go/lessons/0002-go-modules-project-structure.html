Go — Lesson 2

Modules & Project Structure

Your TS mental model: package.json + tsconfig.json + src/. Today you'll map that to Go's equivalent — go.mod, packages, and the directory layout you'll use for your HTTP server.

1. The TS→Go mental-model map

Go has its own module system, but the concepts are familiar. Here's a direct translation of what you already know:

TypeScript
Go
package.json — project manifest, records module name + deps
go.mod — same idea; records module path + Go version + deps
npm install some-lib
go get github.com/some/lib
node_modules/
$GOPATH/pkg/mod/ (shared module cache, not per-project)
package-lock.json / yarn.lock
go.sum — auto-managed; commit it, don't edit it
A file exports symbols via export
A directory is a package; exported symbols start with a capital letter
import { foo } from './bar'
import "mymodule/bar" (by module path, not relative)
ts-node src/index.ts
go run ./main.go or go run .
tsc && node dist/index.js
go build . → produces a single binary, run it directly

2. Initializing a module

Every Go project starts with one command. The module path is the canonical import path for your code — by convention it's a GitHub URL (even if the repo doesn't exist yet).

1
Create a directory and cd into it: 
mkdir my-server && cd my-server
2
Initialize the module: 
go mod init github.com/yourname/my-server
This creates go.mod.
3
Inspect what was created: 
// go.mod
module github.com/yourname/my-server

go 1.22
That's literally all it contains — two lines. Dependencies get added automatically when you go get them.
No npm install needed for stdlib. Go's standard library (net/http, encoding/json, etc.) is bundled with the Go toolchain. You only need go get for third-party packages.

3. Packages: directories, not files

This is the biggest mental-model shift from TS. In TypeScript, each file is a module. In Go, each directory is a package. All .go files in the same directory share the same package name (declared at the top of each file) and can see each other's unexported identifiers.

TypeScript
Go
// src/greet.ts
export function greet(name: string) {
  return `Hello, ${name}`;
}

// src/main.ts
import { greet } from './greet';
console.log(greet("Amit"));
// greet.go  (same dir as main.go)
package main

func Greet(name string) string {
  return "Hello, " + name
}

// main.go
package main

import "fmt"

func main() {
  fmt.Println(Greet("Amit"))
}

Exported = capitalized. Greet is exported (accessible from other packages). greet would be package-private. No export keyword needed — the capital letter is the signal.

4. Project structure for your HTTP server

Here's the layout you'll build toward over the next few lessons. You don't need to create it all now — just recognize the pattern:

my-server/ ├── go.mod # module declaration (= package.json) ├── go.sum # dependency checksums (= package-lock.json) ├── main.go # package main — entry point, starts the server └── handlers/ └── hello.go # package handlers — HTTP handler functions

When handlers/hello.go declares package handlers, you import it in main.go as: 

import "github.com/yourname/my-server/handlers"

Note the full module path, not a relative path. Go always imports by full path. This feels weird at first if you're used to ./handlers, but it means imports are globally unambiguous.

5. Running & building

TypeScript
Go
ts-node src/index.ts — compile + run in one step
go run . — compile + run in one step (same idea)
tsc → node dist/index.js
go build . → ./my-server (single static binary, no runtime needed)
tsc --watch
No built-in watch; use air or watchexec for dev
One binary, zero dependencies. go build produces a fully self-contained binary. No Node.js, no npm packages to ship — just the file. This is one of Go's biggest production advantages.
