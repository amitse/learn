Go for TypeScript Devs — Lesson 10 of the HTTP Server series

Project Layout at Scale

Go Project Structure Packages internal/ ~8 min read

You've built a working HTTP server — routing, JSON, middleware, error handling, tests. Right now it probably lives in one or two files. That's fine for a prototype. But real projects split across packages. This lesson shows you exactly how.

The Problem

Imagine your main.go is 400 lines. It has route wiring, handler logic, custom error types, middleware, and JSON helpers all mixed together. In TypeScript you'd split this into modules. Go has the same idea — but the mechanism is packages, not files.

A package is a directory. Every .go file in the same directory belongs to the same package and can see each other's unexported identifiers — no import needed. A package is the unit of encapsulation in Go.

The Standard Layout

There's no official Go project layout enforced by the toolchain, but the community has converged on a pattern. Here's what a well-structured HTTP server looks like:

myserver/ ├── go.mod ← module root (module myserver) ├── go.sum ├── cmd/ │ └── server/ │ └── main.go ← thin entry point: wire up + listen └── internal/ ← private to this module (compiler-enforced) ├── handlers/ │ ├── users.go ← handler funcs for /users routes │ └── users_test.go ├── middleware/ │ └── logging.go └── apperrors/ └── errors.go ← shared AppError type & sentinels

Reference: go.dev — Module layout · golang-standards/project-layout

The key decisions here:

  • cmd/server/main.go — the binary entry point. It imports and wires up your packages but contains no business logic.
  • internal/ — everything here is private to your module. The Go compiler refuses to compile any code outside this module that tries to import from internal/.
  • Short, lowercase package names — handlers, not userHandlers. The directory name is the package name (by strong convention).

What internal/ Actually Enforces

internal/ is special to the Go compiler. The rule is: only code rooted at the parent of internal/ may import it.

So if your module is myserver:

  • ✅ myserver/cmd/server can import myserver/internal/handlers
  • ✅ myserver/internal/middleware can import myserver/internal/apperrors
  • ❌ Some other module (github.com/someone/other) cannot import myserver/internal/anything
Rule of thumb: For an application server, put everything in internal/. Only move things to a top-level package (e.g. pkg/) if you intentionally plan to publish them as a library for others to import.

Importing Your Own Sub-Packages

You import your own packages using the full module path from go.mod. If your go.mod says module myserver, then: 

import (
    "myserver/internal/handlers"
    "myserver/internal/middleware"
    "myserver/internal/apperrors"
)

This is exactly like TypeScript's import { ... } from '@/handlers/users' with a path alias — except in Go the "alias" is your module name, and it resolves to real filesystem paths automatically.

TS → Go Comparison

TypeScript — splitting modules
// src/handlers/users.ts
export function getUser(req, res) {
  // handle /users/:id
}

// src/errors/AppError.ts
export class AppError extends Error {
  constructor(
    public code: number,
    message: string
  ) { super(message); }
}

// src/index.ts  (thin entry point)
import { getUser } from './handlers/users';
import { AppError } from './errors/AppError';
app.get('/users/:id', getUser);
Go — splitting packages
// internal/handlers/users.go
package handlers

func GetUser(
  w http.ResponseWriter,
  r *http.Request,
) { /* handle /users/{id} */ }

// internal/apperrors/errors.go
package apperrors

type AppError struct {
  Code    int
  Message string
}
func (e *AppError) Error() string { ... }

// cmd/server/main.go  (thin entry point)
import (
  "myserver/internal/handlers"
)
mux.HandleFunc("/users/{id}", handlers.GetUser)

The biggest difference: TypeScript exports/imports individual symbols. Go imports a whole package and uses packagename.Symbol. Unexported symbols (lowercase) stay invisible outside the package.

Package Naming Rules

RuleGoodAvoid
Lowercase, one word handlers, middleware Handlers, myHandlers
No underscores or hyphens apperrors app_errors, app-errors
Match the directory name internal/handlers/ → package handlers package h (misleading)
Avoid "util", "common", "misc" httputil, jsonutil utils (too vague — nothing to import call-site)

The Thin main.go

Once you split into packages, main.go becomes a wiring file. It creates dependencies, registers routes, and starts the server. No business logic lives here. 

// cmd/server/main.go
package main

import (
    "log"
    "net/http"

    "myserver/internal/handlers"
    "myserver/internal/middleware"
)

func main() {
    mux := http.NewServeMux()

    mux.HandleFunc("GET /users/{id}", handlers.GetUser)
    mux.HandleFunc("POST /users",     handlers.CreateUser)

    logged := middleware.Logging(mux)

    log.Println("listening on :8080")
    log.Fatal(http.ListenAndServe(":8080", logged))
}
Tip: cmd/server/ can be built with go build ./cmd/server. You can have multiple binaries under cmd/ — e.g. cmd/migrate/, cmd/worker/ — each with their own main.go.

Shared Types Across Packages

A common question: where do shared types live? For an application, put them in their own package. Error types go in internal/apperrors, domain types (User, Order, etc.) might go in internal/domain.

internal/apperrors/errors.go
package apperrors

import "fmt"

type AppError struct {
    Code    int
    Message string
}

func (e *AppError) Error() string {
    return fmt.Sprintf("%d: %s", e.Code, e.Message)
}

var ErrNotFound = &AppError{
    Code:    404,
    Message: "not found",
}
internal/handlers/users.go
package handlers

import (
    "errors"
    "net/http"

    "myserver/internal/apperrors"
)

func GetUser(
    w http.ResponseWriter,
    r *http.Request,
) {
    id := r.PathValue("id")
    user, err := findUser(id) // unexported fn, same pkg
    if errors.Is(err, apperrors.ErrNotFound) {
        http.Error(w, "not found", 404)
        return
    }
    // ... encode user as JSON
}

What You Can Build Right Now

Try refactoring your lesson 7 mini-server into this layout. The steps:

  1. Create internal/handlers/, internal/middleware/, internal/apperrors/
  2. Move handler functions into internal/handlers/users.go (or similar), add package handlers at the top
  3. Move middleware into internal/middleware/logging.go
  4. Move AppError + sentinels into internal/apperrors/errors.go
  5. Create cmd/server/main.go — import and wire everything up
  6. Run: go build ./cmd/server && ./server
Build the whole module: go build ./... compiles every package. go test ./... runs every test. The ./... wildcard is your friend.

Key Takeaways

  • Package = directory. All .go files in the same directory share a package.
  • internal/ is compiler-enforced privacy — only your module can import it.
  • Import via full module path — "github.com/you/myserver/internal/handlers".
  • Thin main.go — wire up, don't implement. Business logic lives in packages.
  • Avoid util — name packages after what they contain, not how they're used.
