Adapt JWT claims to an operations principal

Lesson 51 made LogLevelControl require a trusted Principal. Now connect the JWT middleware from Lesson 16 without making the control depend on HTTP or treating a request header as authority.

Tangible win

You will add one adapter that turns already-verified JWT claims into an application Principal. An admin handler gets the principal from the request context and passes it explicitly to the control; the control keeps enforcing logs:write.

Keep three jobs separate

  1. Authentication middleware verifies the token signature and expiry, then stores typed claims in request context.
  2. The adapter translates those claims into your application’s authority model.
  3. The control authorizes the operation and changes the log level only for a permitted principal.

This gives each layer one question: “who is this?”, “what can this identity do here?”, and “may this operation proceed?”

Make the translation explicit

Reuse Lesson 16’s private context key and typed Claims. The adapter is the only place that knows both the JWT shape and your application’s Principal shape.

// package auth
var ErrNoPrincipal = errors.New("authenticated principal missing")

type Principal struct {
    ID          string
    Permissions map[string]bool
}

func (p Principal) Can(permission string) bool { return p.Permissions[permission] }

func PrincipalFromContext(ctx context.Context) (Principal, error) {
    claims, ok := ctx.Value(ClaimsKey).(*Claims)
    if !ok || claims.Subject == "" {
        return Principal{}, ErrNoPrincipal
    }

    permissions := map[string]bool{}
    // This mapping is application policy—not a client-provided header.
    if claims.Role == "operator" {
        permissions["logs:write"] = true
    }
    return Principal{ID: claims.Subject, Permissions: permissions}, nil
}

The Role claim must have been inside the token that the middleware verified. The mapping remains server-owned: a role receives only permissions your code defines. For a larger system, this seam can consult a policy service or database—but not inside the log-level control itself.

Why not pass *Claims into Set? Claims are transport/authentication data. Principal describes the capability the application operation needs. Keeping that boundary lets a CLI or job construct the same principal without fabricating an HTTP request or JWT.

Use the adapter at the HTTP edge

func SetDebug(control *LogLevelControl) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        principal, err := auth.PrincipalFromContext(r.Context())
        if err != nil {
            http.Error(w, "unauthorized", http.StatusUnauthorized)
            return
        }
        if err := control.Set(r.Context(), principal, slog.LevelDebug); err != nil {
            if errors.Is(err, ErrForbidden) {
                http.Error(w, "forbidden", http.StatusForbidden)
                return
            }
            http.Error(w, "internal error", http.StatusInternalServerError)
            return
        }
        w.WriteHeader(http.StatusNoContent)
    }
}

Route composition determines whether claims exist:

mux.Handle("POST /ops/log-level/debug",
    AuthMiddleware(secret)(SetDebug(control)),
)
401 is not 403. No verified identity (or malformed context) is 401 Unauthorized. A verified identity that lacks logs:write is 403 Forbidden. Keep the control’s sentinel ErrForbidden; the HTTP handler translates it at the transport boundary.

Test the seam, not a real token

func TestPrincipalFromContextOperatorCanWriteLogs(t *testing.T) {
    claims := &Claims{RegisteredClaims: jwt.RegisteredClaims{
        Subject: "ops-17",
    }, Role: "operator"}
    ctx := context.WithValue(context.Background(), ClaimsKey, claims)

    got, err := PrincipalFromContext(ctx)
    if err != nil { t.Fatal(err) }
    if got.ID != "ops-17" || !got.Can("logs:write") {
        t.Fatalf("principal = %#v, want operator with logs:write", got)
    }
}
