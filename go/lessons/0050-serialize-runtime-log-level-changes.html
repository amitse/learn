Serialize runtime log-level changes

A slog.LevelVar safely permits concurrent reads and writes. But safe access is not the same as an ordered audit history: two callers can otherwise interleave “read old level → set new level → audit”.

Tangible win

You will make one log-level change operation atomic as a business action: read the old level, set the new one, and submit its audit record while one control mutex is held. A focused test proves two concurrent changes produce a coherent transition chain.

Thread-safe value ≠ ordered operation

LevelVar is safe for concurrent use, so using Set from two goroutines will not create a data race. Yet this unprotected sequence can report an impossible-looking history:

// Goroutine A reads INFO
// Goroutine B reads INFO, sets WARN, audits INFO → WARN
// Goroutine A sets DEBUG, audits INFO → DEBUG
// Final level: DEBUG. The audit claims both changes began at INFO.

The missing guarantee is not memory safety; it is a serial order for the whole state-change-and-audit operation.

TypeScript / Node

// A single async mutex protects the transaction.
await mutex.runExclusive(() => {
  const from = level.current;
  level.current = to;
  audit.info({ actor, from, to },
    "log level changed");
});

Go

type LogLevelControl struct {
    mu    sync.Mutex
    level *slog.LevelVar
    audit *slog.Logger
}

func (c *LogLevelControl) Set(
    ctx context.Context, actor string, to slog.Level,
) {
    c.mu.Lock()
    defer c.mu.Unlock()

    from := c.level.Level()
    c.level.Set(to)
    c.audit.InfoContext(ctx, "log level changed",
        "actor", actor, "from", from, "to", to)
}
Scope the lock to the contract: this mutex belongs inside the one application-owned control from Lesson 49. It does not wrap normal application logging or HTTP handlers. Those keep reading the shared LevelVar concurrently.

What this ordering guarantees

Within this process, callers of this one control see a serial sequence. If the events are INFO → WARN and then WARN → DEBUG, the second event’s from is the first event’s to.

// The control owns both the mutable policy and the operation lock.
func NewLogLevelControl(level *slog.LevelVar, audit *slog.Logger) *LogLevelControl {
    return &LogLevelControl{level: level, audit: audit}
}
Important limit: a mutex orders method execution and synchronous submission to your configured handler. It cannot guarantee that an external collector, buffered transport, or distributed audit system stores events in that same order. If retention order matters, choose and test a sink that explicitly provides that guarantee.

Test a transition chain, not scheduling

Do not test that a particular goroutine “wins”; scheduling is deliberately unspecified. Start two changes concurrently, wait for both, decode the two audit events, and check that together they form one valid chain from INFO through WARN and DEBUG.

func TestLogLevelControlSerializesTransitions(t *testing.T) {
    var out bytes.Buffer
    var level slog.LevelVar
    level.Set(slog.LevelInfo)
    audit := slog.New(slog.NewJSONHandler(&out, nil))
    control := NewLogLevelControl(&level, audit)

    var wg sync.WaitGroup
    for _, to := range []slog.Level{slog.LevelWarn, slog.LevelDebug} {
        wg.Add(1)
        go func(to slog.Level) {
            defer wg.Done()
            control.Set(context.Background(), "on-call:amit", to)
        }(to)
    }
    wg.Wait()

    // Decode the two newline-delimited JSON records. In emitted order,
    // require events[1]["from"] == events[0]["to"]. Also require the
    // first "from" is INFO and the final control level equals the last "to".
}

Run this test with go test -race ./.... The race detector helps expose unsynchronized memory access; the chain assertion verifies the higher-level ordering rule your operators need.

Do this now

  1. Add sync.Mutex to the existing LogLevelControl, not to handlers or the logger factory.
  2. Hold it across Level(), Set(), and synchronous audit submission.
  3. Keep the audit logger independent of the mutable application threshold.
  4. Add the two-change chain test, then run go test -race ./....
  5. Only promise cross-process ordering if the audit destination documents it.
