Goroutines & the HTTP Server's Concurrency Model

🎯 Mission: ship an HTTP server in Go

Why you need to know this

Your HTTP server is already running. But every time a request hits it, Go does something invisible that makes the whole thing work at scale: it spawns a goroutine. Understanding goroutines takes you from "my server works" to "I know what my server is doing and why it doesn't fall over under load." This lesson is mission-critical, not optional.

⚡ The one thing to remember
net/http calls your handler in its own goroutine — one per request, automatically, for free. You didn't write go anywhere, but concurrency is already happening in every server you've built so far.

What is a goroutine?

A goroutine is Go's unit of concurrent execution — lighter than an OS thread, managed by the Go runtime scheduler. [go.dev/tour: goroutines]

TypeScript async

// async/await: one event loop thread,
// work pauses at 'await'
async function handleRequest() {
  const data = await fetchDB();
  return data;
}
// Node.js processes one request at a time
// but yields at I/O — single-threaded

Go goroutines

// goroutines: truly concurrent,
// OS-level parallelism on multi-core
func handleRequest(w, r) {
  data := fetchDB()  // blocks this goroutine
  // other goroutines run freely meanwhile
}
// net/http runs each request in its own goroutine

Spawning a goroutine

You launch one with the go keyword in front of a function call:

go someFunction()          // fire and forget — runs concurrently
go func() {
    fmt.Println("I run concurrently")
}()
Cost: A goroutine starts with a ~2 KB stack (grows as needed). An OS thread starts with ~1 MB. Go easily runs millions of goroutines on modest hardware. A busy HTTP server might have thousands in flight at once — that's fine. [go.dev/faq: goroutines]

How net/http uses goroutines

When you call http.ListenAndServe, the standard library's server loop does something like this under the hood: [src/net/http/server.go] 

// Simplified from net/http/server.go
for {
    conn, _ := listener.Accept()  // wait for next connection
    go handleConn(conn)           // ← each connection gets its own goroutine
}

And inside handleConn, each HTTP request in a keep-alive connection also runs in a goroutine. Your handler is always called from a goroutine — you never need to manage this yourself.

📌 What this means for your code
Your handlers run concurrently. Two requests can execute the same handler at the same time, in different goroutines. Any shared state you read/write from a handler must be protected — or you have a race condition.

Race conditions: the one gotcha

If two goroutines read and write the same variable without synchronisation, you have a data race. Go has a built-in race detector to catch this: 

// BAD — shared counter without protection
var count int  // package-level variable

func CountHandler(w http.ResponseWriter, r *http.Request) {
    count++  // 🚨 RACE: two requests can do this simultaneously
    fmt.Fprintf(w, "count: %d", count)
}
// GOOD — protect with sync.Mutex
import "sync"

var (
    count int
    mu    sync.Mutex
)

func CountHandler(w http.ResponseWriter, r *http.Request) {
    mu.Lock()
    count++
    mu.Unlock()
    fmt.Fprintf(w, "count: %d", count)
}
Run the race detector while developing: go run -race main.go or go test -race ./.... It instruments your binary to detect concurrent access violations at runtime. No performance cost in production — just leave -race off in your release builds. [go.dev: race detector]

Practical pattern: background work in a handler

Sometimes you want to fire off work (e.g. logging, sending an email) without making the user wait. Use a goroutine — but be careful about closures: 

func CreateUserHandler(w http.ResponseWriter, r *http.Request) {
    user := parseUser(r)

    // Respond immediately
    w.WriteHeader(http.StatusAccepted)

    // Do slow work in the background — don't block the response
    go func(u User) {
        sendWelcomeEmail(u)      // could take seconds
        logUserCreation(u)
    }(user)               // pass user as arg — avoid closure capture bug
}
Closure capture gotcha: If you write go func() { use(user) }() instead of passing user as an argument, and user gets reassigned later in the same scope, your goroutine will see the updated value — not what you intended. Always pass loop variables and mutating locals as arguments.

TS async vs Go goroutines — mental model

Concept TypeScript Go
concurrency unit Promise / async task goroutine
parallelism single-threaded (Node.js); multi-thread via workers multi-core by default, via runtime scheduler
start async work someAsync().then(...) go someFunc()
wait for result await channel receive: result := <-ch
shared state protection usually not needed (single-thread) sync.Mutex or channels
HTTP handler concurrency event loop, one at a time at CPU level each request = own goroutine, truly parallel

Channels — quick teaser

Goroutines communicate via channels — typed pipes you can send values into and receive from. You don't need them for the HTTP server mission, but they're how Go coordinates concurrent work: [go.dev/tour: channels] 

// Create a channel of ints
ch := make(chan int)

// Send in a goroutine
go func() { ch <- 42 }()

// Receive — blocks until the value arrives
result := <-ch
fmt.Println(result) // 42

Channels are covered in depth beyond the HTTP server scope — but now you know they exist and what they're for.
